create table public.products (
  id bigint generated by default as identity not null,
  seller_id uuid not null,
  store_id bigint null,
  category_id uuid null,
  name text null,
  slug text null,
  description text null,
  price numeric null,
  stock numeric null,
  condition text null,
  status text null,
  is_featured boolean not null default false,
  featured_until timestamp with time zone null,
  discount_price numeric null,
  offer_ends_at timestamp with time zone null,
  created_at timestamp with time zone not null default now(),
  updated_at timestamp with time zone null default now(),
  images text[] null,
  sale_type text null,
  is_auction boolean null,
  shipping_available boolean null,
  starting_price numeric null,
  current_bid numeric null,
  bid_increment numeric null,
  auction_ends_at timestamp with time zone null,
  winner_id uuid null,
  constraint products_discount_price_lt_price_check
    check (discount_price is null or (price is not null and discount_price < price)),
  constraint fk_products_profiles
    foreign key (seller_id) references public.profiles(id),
  constraint products_pkey primary key (id)
) TABLESPACE pg_default;

`products.category_id` stores the UUID identifier from `public.categories`. Keep category IDs as strings in the web client; `seller_id` separately stores the authenticated user's UUID. Apply [`20261019000000_align_product_category_uuid.sql`](../supabase/migrations/20261019000000_align_product_category_uuid.sql) to migrate installations where `products.category_id` is still `BIGINT`. The previous numeric column is retained as `legacy_category_id`; reassign those legacy values to categories through the product editor because they cannot be automatically mapped to UUIDs.

En la base de datos actual, `status` es texto y el valor `'true'` representa una publicación activa. Los campos promocionales permiten fechas de expiración nulas cuando la promoción correspondiente está desactivada.

BUCKET NAME:

product-images

La columna `images` almacena las URLs públicas de Storage como `text[]`. En bases existentes donde esta columna aún sea `json`, debe convertirse antes de desplegar esta funcionalidad; conserva arreglos JSON de cadenas y aborta ante valores que no sean arreglos:

```sql
CREATE FUNCTION public._json_images_to_text_array(value json)
RETURNS text[]
LANGUAGE sql
IMMUTABLE
AS $$
  SELECT CASE
    WHEN value IS NULL THEN NULL
    ELSE COALESCE(array_agg(image), ARRAY[]::text[])
  END
  FROM json_array_elements_text(value) AS elements(image)
$$;

ALTER TABLE public.products
  ALTER COLUMN images TYPE text[]
  USING public._json_images_to_text_array(images);

DROP FUNCTION public._json_images_to_text_array(json);
```

La relación `products.seller_id` referencia `profiles.id` mediante la restricción `fk_products_profiles`. Las consultas de detalle cargan el nombre del vendedor con `seller:profiles!fk_products_profiles (id, full_name)`. Los productos muestran una tienda asociada cuando `store_id` apunta a una fila de `public.stores` con columna `name`.

Las publicaciones destacadas usan `is_featured` y `featured_until`. La publicidad usa Webpay Plus de integración: el producto primero se inserta como publicación normal y solo después de confirmar que está activo se inicia el cobro. El servidor calcula el precio del plan (1, 3, 7 o 14 días), guarda el intento en `product_ad_transactions` y activa el destacado únicamente tras una confirmación autorizada que coincida con la orden y el monto. Si el pago se rechaza o cancela, la publicación permanece activa sin destacar. Los pagos pendientes o ambiguos bloquean un nuevo intento hasta su revisión. La migración `supabase/migrations/20261107150000_webpay_advertising.sql` mantiene la bitácora privada y evita que los clientes modifiquen directamente `is_featured` o `featured_until`; debe aplicarse después de la migración base de Webpay Mall. La portada solo consulta productos con `is_featured = true`, `featured_until` vigente, estado activo y stock disponible.

## Subastas en vivo

Las subastas se almacenan en `public.products`, con `sale_type = 'auction'` y los campos `starting_price`, `current_bid`, `bid_increment`, `auction_ends_at` (`timestamptz`) y `winner_id` (UUID del perfil ganador). El vendedor de una subasta se obtiene desde `public.profiles` por la relación existente `products.seller_id` → `profiles.id`.

Las pujas se registran en `public.bids` con `id`, `product_id` (`BIGINT`), `bidder_id` (`UUID`), `amount` y `created_at`. La interfaz trata los IDs `BIGINT` como `number` de JavaScript. No debe insertar pujas directamente: el envío se realiza exclusivamente mediante la RPC transaccional existente:

```ts
supabase.rpc("place_bid", {
  p_product_id: productId,
  p_bid_amount: amount,
});
```

Al publicar una subasta, `price`, `discount_price` y `offer_ends_at` quedan nulos; el formulario guarda el monto inicial en `starting_price`, deja `current_bid` y `winner_id` nulos, define un `bid_increment` entero positivo que no supera el 50% del precio inicial y calcula `auction_ends_at` a partir de la duración elegida. En una venta directa, los campos exclusivos de subasta quedan nulos. El perfil retira publicaciones mediante baja lógica (`status = false`) para conservar referencias e historial de pujas.

La migración `supabase/migrations/20261005170000_enforce_auction_bid_limits.sql` instala un trigger `BEFORE INSERT` en `public.bids`. El trigger bloquea la subasta asociada y rechaza importes fraccionarios, menores que el mínimo configurado (`starting_price` para la primera puja; puja más alta previamente registrada + `bid_increment` después) o mayores que `floor(referencia × 1,5)`. La referencia es `starting_price` antes de la primera puja y la puja más alta existente en los turnos siguientes, que corresponde a `current_bid`. El trigger excluye la puja que está insertándose, de modo que la regla no depende de si la RPC actualiza `current_bid` antes o después del INSERT. Esta validación de base de datos es obligatoria además de la validación de la interfaz; debe desplegarse en Supabase para proteger las llamadas RPC y cualquier otra ruta de inserción.

La migración `supabase/migrations/20260929140000_fix_anti_sniping_status_type.sql` instala el trigger diferido sobre `public.bids`. La función compara `products.status` con el texto `'true'`; cuando una puja se confirma con hasta tres minutos y treinta segundos restantes, extiende `auction_ends_at` cinco minutos dentro de la misma transacción. Las pujas posteriores pueden volver a extender el cierre. Aplicar esta migración en Supabase; la sala sincroniza el nuevo vencimiento mediante el UPDATE de `products` publicado en Realtime.

`public.products` y `public.bids` deben estar incluidas en la publicación `supabase_realtime`. Solo la sala individual `/subastas/[id]` abre un canal, con eventos filtrados por el ID de su producto (`bids` INSERT por `product_id`, `products` UPDATE por `id`) y retira la suscripción al desmontarse. El catálogo `/subastas`, el Home y `/tienda` utilizan consultas estándar; no abren canales de Realtime.

La tabla `public.messages` también debe estar incluida en `supabase_realtime` para que los mensajes nuevos se entreguen a las salas abiertas sin recargar. La migración `supabase/migrations/20261015160000_enable_messages_realtime.sql` agrega la tabla de forma idempotente; aplícala al proyecto Supabase junto con `REPLICA IDENTITY FULL` y las políticas RLS descritas en [schema.md](../apps/web/lib/supabase/schema.md).

## Carrito de compras

El contrato requerido por la sincronización de la aplicación usa `public.carts` y `public.cart_items`. Cada carrito pertenece a un usuario autenticado; `cart_items.cart_id` es UUID y `cart_items.product_id` es BIGINT, con una fila única por producto y carrito. Las políticas RLS deben limitar lectura y mutaciones al propietario.

En el checkout actual del repositorio no se encontró versionada la migración `20260928000000_shopping_cart.sql`; verificar que estas tablas, restricciones e índices estén creados en Supabase antes de depender de la sincronización entre dispositivos. La aplicación considera compra directa los valores existentes `sale_type = 'direct'` y `sale_type = 'fixed_price'`; excluye subastas y valida la información actual del producto al fusionar el carrito. El detalle del flujo está en [CART.md](./CART.md).

## Órdenes y Webpay Plus Mall

Las órdenes y sus políticas RLS existentes siguen usando `orders` y `order_items`. El checkout Webpay está versionado en [`supabase/migrations/20261105200000_webpay_plus_mall.sql`](../supabase/migrations/20261105200000_webpay_plus_mall.sql): separa la orden Vindex, el registro padre `payment_transactions` y sus hijos `payment_subtransactions`. El registro padre conserva orden Mall, token, estado y respuesta de auditoría; cada hijo conserva comercio lógico, código, orden, monto y resultado individual. Las tablas de pago no son legibles por los roles de cliente.

El checkout crea la orden como `pending_payment` desde datos de `carts`, `cart_items` y `products` consultados en una RPC de servidor. El comprador no envía precios, stock ni identidad de vendedor como fuente de verdad. Una autorización total termina en `paid`; autorizaciones parciales en `partially_paid`; rechazos en `payment_failed`; resultados que no se pueden verificar quedan en `payment_review`. El flujo de operación y la matriz de pruebas están en [WEBPAY_PLUS_MALL.md](./WEBPAY_PLUS_MALL.md).

Las RPC de pago se conceden solo a `service_role`. Las rutas validan sesión y propiedad con el cliente SSR y después usan `SUPABASE_SERVICE_ROLE_KEY` exclusivamente en el servidor. No despliegues el checkout hasta configurar esa clave de servidor y `NEXT_PUBLIC_SITE_URL` HTTPS; no expongas ninguna clave secreta en variables `NEXT_PUBLIC_*`. La migración protege importes y estados de `orders` frente a actualizaciones desde roles de cliente y revoca a estos la RPC antigua `process_mock_checkout`; las órdenes simuladas históricas no se modifican.

La página de confirmación y el historial del perfil consultan órdenes visibles mediante RLS. Los productos referenciados se consultan por separado para representar también las líneas cuyo producto haya sido eliminado. Las calificaciones usan la tabla `reviews`, cuyos campos y políticas deben permitir la inserción del comprador; el cliente habilita esa acción únicamente para órdenes `completed` o `delivered`.

La RPC obtiene las líneas del carrito uniendo `cart_items.cart_id` con `carts.id` y filtrando por `carts.user_id`. Si la RPC desplegada referencia `cart_items.user_id`, aplicar [`supabase/migrations/20261015195500_fix_mock_checkout_cart_lookup.sql`](../supabase/migrations/20261015195500_fix_mock_checkout_cart_lookup.sql); el esquema usado por la aplicación no tiene esa columna en `cart_items`.

Para diferenciar el retiro presencial, el checkout guarda `Acordar con el vendedor` en `shipping_address`; no se infiere el tipo de entrega a partir del costo. El código de seis dígitos se genera solo después de autorizar todas las subtransacciones; antes de eso no existe un OTP disponible. `get_buyer_delivery_code(p_order_id)` y `verify_delivery_otp(p_order_id, p_entered_code)` deben seguir validando la propiedad de la orden. La migración Webpay impide cambiar el código o estado de entrega mientras el pago no esté autorizado.

Para Webpay, el stock se reserva lógicamente mientras el pago está pendiente, sin descontarse dos veces. Una orden estándar autorizada descuenta stock al finalizar el pago; una orden de retiro lo descuenta con el OTP mediante la migración [`20261016194000_decrement_stock_after_pickup.sql`](../supabase/migrations/20261016194000_decrement_stock_after_pickup.sql). Los listados públicos omiten productos sin stock; el vendedor mantiene acceso a sus publicaciones en el perfil y puede editar su stock para volver a ofrecerlas.

En bases donde el checkout y la RPC OTP ya fueron desplegados, aplicar también la migración incremental [`20261015194100_secure_delivery_code_access.sql`](../supabase/migrations/20261015194100_secure_delivery_code_access.sql) para restringir el acceso directo al código y habilitar su consulta segura por el comprador.
